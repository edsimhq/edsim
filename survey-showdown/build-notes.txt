PEDAGOGICAL INTENT
------------------
Survey Showdown is modeled on Family Feud but grounded in real
Regents exam content. The "100 historians were polled" framing
serves a specific purpose: it repositions historical knowledge
as something that exists on a spectrum of importance rather than
as a binary right/wrong. Students who know "taxation without
representation" is the top answer AND why it ranks above
"quartering of troops" understand the content more deeply than
students who can simply recall both facts.

The point ranking system (38 pts vs 10 pts) is not arbitrary —
it reflects how frequently each answer appeared in Regents
responses. This is real data, not invented difficulty.

The word bank feature was added specifically for differentiation.
A teacher running the same game with two different periods can
dial the scaffold up or down without changing the content.
Fewer phantoms = more scaffolded. More phantoms = harder because
correct answers are buried in more noise. This gives teachers
a live differentiation lever that doesn't exist in most edtech.


ARCHITECTURE OVERVIEW
----------------------
Survey Showdown is a fully static HTML application. No server,
no database, no build step. All files are plain HTML/CSS/JS
(except the Ably real-time integration for class mode sync —
see CLASS MODE SYNC section below).

Files:
  index.html          Home page and mode selector
  host.html           Teacher dashboard (password protected)
  game-class.html     Student scoreboard (projected/shared view)
  game-wordbank.html  Solo mode (individual student play)
  audio.js            AudioEngine — Web Audio API sound effects
  data/               JSON unit files (11 units, reference only)
                      Note: all unit data is embedded directly
                      in host.html and game-wordbank.html as
                      const UNITS = {...}. The /data/ folder
                      contains the source JSON files for
                      reference and future use.

No frameworks. No npm. No build pipeline. Ably is the only
external dependency (loaded via CDN in game-class.html and
host.html for real-time class mode sync).


CLASS MODE SYNC — ABLY REAL-TIME
----------------------------------
Class Mode uses Ably (managed WebSocket infrastructure) to sync
state between the teacher dashboard (host.html) and the student
scoreboard (game-class.html). This enables cross-device sync —
the scoreboard can run on a projector, a student's Chromebook,
or any device with a browser.

How it works:
  - Teacher generates (or enters) a 4-digit room code in host.html
  - host.html connects to Ably and publishes state snapshots to
    a channel named 'feud-room-XXXX' (where XXXX = room code)
  - game-class.html prompts for the room code, then subscribes
    to the same Ably channel
  - Every state change in host.html calls broadcastState(), which
    publishes a complete state snapshot via Ably
  - game-class.html receives the message via channel.subscribe()
    and calls applyState() to re-render

The Ably API key is embedded in both host.html and game-class.html.
Key: see ABLY KEY section below.

IMPORTANT: Unlike BroadcastChannel (same-machine only), Ably
works across devices and networks. The scoreboard does not need
to be on the same physical machine as the teacher dashboard.

Previous architecture (v4.0): used browser BroadcastChannel API
(same-machine, same-browser only). Replaced with Ably in v4.1+
to enable cross-device classroom use.


ABLY KEY
---------
The Ably API key is embedded directly in host.html and
game-class.html. It is a client-side publish/subscribe key
scoped to this application only.

Key location in code: const ABLY_KEY = '...'
Ably dashboard: https://ably.com (log in to rotate or revoke)

Note: The key is visible in source code. This is acceptable for
a classroom-scale EdSim application — it controls access to a
single pub/sub channel namespace, not sensitive data. Students
seeing the key cannot access other rooms or extract student data.
If the key is ever abused, rotate it in the Ably dashboard and
update both HTML files.


WORD BANK — PHANTOM ANSWER LOGIC
----------------------------------
The word bank in both Solo Mode and Class Mode uses "phantom"
answers — real answers from OTHER rounds in the same unit —
as distractors. This is intentional: phantom answers are
historically plausible (they come from the same content area)
but contextually wrong (they don't belong to this question).

This is harder than random distractors and more pedagogically
honest. A student who confuses "Containment of communism" with
a Cold War domestic policy answer is making a meaningful error
worth addressing, not a random guess.

Phantom generation (buildBank in game-wordbank.html,
buildWordBank in host.html):
  1. Collect all answers from rounds OTHER than current round
  2. Shuffle the pool
  3. Take the first N answers (N = phantom slider value)
  4. Combine with 5 real answers and shuffle again

Phantom count range: 0–10, default 5.
  0 phantoms = only real answers shown (easiest)
  10 phantoms = 5 real buried in 15 chips (hardest)

SLIDER TIMING NOTE: The phantom slider value is read at round
load time (inside buildBank/buildWordBank), not at game start.
This means a teacher can adjust the slider mid-game and the
change takes effect on the next round. This is intentional —
it allows real-time difficulty adjustment during class.

MINIMUM ROUND POLICY: Units must have at least 3 rounds to be
published on EdSim. A 3-round unit has 10 phantom candidates
available (2 other rounds × 5 answers), which exactly covers
the maximum phantom count of 10. Units with fewer rounds should
be expanded or combined with a thematically related unit before
publishing.

All 11 current units have 6 rounds = 25 phantom candidates.
The phantom shortfall scenario cannot occur with current content.


AUDIO ENGINE
-------------
audio.js contains a lightweight AudioEngine built on the Web
Audio API. All sounds are synthesized programmatically — no
audio files, no external assets, no loading time.

Sounds:
  AudioEngine.reveal()          Answer revealed
  AudioEngine.strike()          Wrong answer / strike
  AudioEngine.roundWin()        All answers found
  AudioEngine.steal()           3 strikes, steal offered
  AudioEngine.stealWin()        Steal successful
  AudioEngine.stealFail()       Steal failed
  AudioEngine.questionReveal()  New round loaded
  AudioEngine.multiplierStart() Multiplier round begins

The engine gracefully handles browsers that block autoplay —
sounds simply don't play if the AudioContext can't be created.

AI FEEDBACK (SOLO MODE)
------------------------
Solo mode includes optional feedback on wrong answers. When
enabled, clicking a wrong chip displays a brief explanation
of why that answer doesn't fit the current question.

The feedback is hardcoded — each answer in UNITS carries an
"explanation" field written by the teacher-creator. When a
student clicks a phantom answer, showAIFeedback() looks up
the matching answer object in gameData.rounds and displays
its explanation field instantly.

No API call. No network request. No cost. Works offline.
The feedback panel appears immediately with no loading state.

If an answer has no explanation field, the panel does not
appear — it fails silently. All 330 answers across all 11
units currently have explanations.

The "explanation" field lives on each answer object in UNITS:
  { "text": "Containment of communism", "points": 40,
    "explanation": "This is a Cold War strategy — Kennan's
    containment doctrine held that the US should prevent
    Soviet expansion without directly attacking the USSR." }

When adding new units, include an explanation for each answer.
The explanation should say what topic the answer DOES belong
to, not just that it's wrong — students need the correct
context, not just a correction.

Note: The Netlify Function (netlify/functions/ai-feedback.js)
was built but is no longer used. It can be removed on next
deploy or retained for a potential future "custom question"
mode where content isn't pre-authored.


DATA LOADING — game-class.html
--------------------------------
game-class.html receives ALL game data via Ably state messages
from host.html. It does not load unit data independently, does
not use the UNITS object, and has no JSON file upload mechanism.

The complete game state (question text, answer texts, scores,
word bank chips, round metadata) is included in every state
snapshot that host.html publishes. game-class.html is a pure
display layer — it renders whatever it receives.

This means game-class.html has no dependency on /data/ JSON
files and no embedded UNITS object. If a unit is updated,
only host.html and game-wordbank.html need to be updated.

Previous versions used a JSON file upload workflow in
game-class.html. This was removed when Ably sync was
implemented — the scoreboard now receives all data from
the host in real time.


UNIT DATA
----------
All 11 units are embedded as a const UNITS = {...} object in
both host.html and game-wordbank.html. This was a deliberate
decision to make both files self-contained — no fetch() calls,
no server required, works offline.

The /data/ folder contains the same units as individual JSON
files. These are the source of truth for content. If a unit
is updated, update both the JSON file AND the embedded object
in both HTML files (host.html and game-wordbank.html).
game-class.html does NOT need to be updated for content changes.

Units:
  colonial-revolution.json
  early-republic.json
  civil-war-reconstruction.json
  industrialization-immigration.json
  progressive-era.json
  wwi-1920s.json
  great-depression-new-deal.json
  world-war-ii.json
  cold-war.json
  civil-rights.json
  modern-america.json

Each unit follows this schema:
  {
    "unit": "Unit Name",
    "poll_label": "100 historians were surveyed...",
    "rounds": [
      {
        "id": "r1",
        "question": "Name a...",
        "multiplier": 1,
        "answers": [
          { "text": "Answer text", "points": 38,
            "explanation": "Context for wrong-answer feedback." },
          ...
        ]
      }
    ]
  }

Points per round must sum to 100.
Multiplier applies to all answer points for that round (1, 2, or 3).
Answers should be ordered highest to lowest points.
Every answer must have an explanation field (used by solo feedback).
